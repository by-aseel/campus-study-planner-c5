# Reflection

I drew the boundaries around information retrieval, persistent change, and coordination. The Data tool, `find_study_resource`, searches a small fictional campus study catalog without changing it. The Action tool, `create_study_task`, saves one task in SQLite from a title, duration, and request identifier; it can be useful even when no catalog lookup is needed. The Orchestration tool, `plan_study_session`, coordinates the same underlying lookup and creation functions to turn a topic into a saved study task. Keeping this sequence in the server makes the rule explicit: a failed resource lookup must not create a task. Shared validation avoids inconsistent behavior between direct calls and the coordinated workflow. The request identifier provides idempotency, so a retry of the same request can return its existing task instead of inserting a duplicate; reusing the identifier for different inputs must fail clearly.

Three tools suit this deliberately narrow use case because each corresponds to a distinct user intention: find material, save a task, or plan study around available material. Combining them into one tool with a mode argument would make the side effect less obvious, while exposing every internal helper would burden the agent with unnecessary choices. The main design tension is that planning includes multiple steps while still needing one clear purpose; explicit sequencing and reuse resolve that tension without duplicating the underlying rules. A next version could replace the fictional catalog with an authenticated university source and add task completion or scheduling as separate capabilities. Those additions should follow concrete user needs, with clear permissions and tests for partial failures, rather than expanding the toolkit merely to increase its size.
